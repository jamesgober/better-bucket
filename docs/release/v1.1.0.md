# better-bucket v1.1.0 — Exact

**The contract, kept.** v1.0.0 promised that the bucket never over-grants, and
under ordinary multi-threaded use with the default clock it granted 36x–527x its
quota. v1.1.0 replaces the accounting core so the promise holds by construction,
removes every representation limit the old core had, and adds the caller-driven
`no_std` core, retry queries, reservations and refunds that 1.x was missing. No
existing call site changes. **Upgrade from 1.0.0.**

## What is better-bucket?

A lock-free token bucket for Rust: one atomic word, one compare-and-swap per
acquire, no allocation, no background thread, refill computed lazily from an
injected monotonic clock — or from a time the caller supplies, in `no_std`.
Token bucket is its sole job; it is the primitive `rate-net` consumes.

## The bug

Each `try_acquire` read the clock once, before its CAS loop. If another thread
committed a later timestamp in between — routine under contention — the stale
reading's `now_ms.wrapping_sub(last_ms)` came out as ~49.7 days, the bucket
refilled to full, and the older timestamp was written back so the next caller
re-credited the interval. Measured on a 1000/s bucket over 1.5 s: 2 threads
granted ~89,000 tokens against a ~2,500 ceiling; 16 threads ~1.37 million. A
custom `Clock` that stepped backwards did the same. Every 1.0 concurrency test
froze the clock, so none of them could see it — including the `loom` model.

## The fix: one instant

The bucket's state is now the single instant at which it would have been empty.
A grant moves that instant forward by the tokens' cost; the tokens are available
if the new instant is not after `now`. That is the token-bucket reading of GCRA,
and it makes a stale or backward reading harmless by construction: it can only
see fewer tokens. There is no subtraction that can wrap and no skew window to
tune — a window either stalls buckets idle for weeks or leaves a smaller
over-grant.

The same change removes the other limits of the 1.0 word:

- **Exact token accounting.** Tokens are counted in binary fractions sized per
  bucket; for every rate up to ~4.3 × 10^9 tokens/second (every `u32` amount per
  second) grants, refunds and the capacity never round, and a bucket with no
  refill conserves every token. Faster buckets round each grant up to a
  multi-token unit.
- **No wrap.** Time is nanoseconds and lasts at least ~438 years below 10^9
  tokens/second (~100 years above), then fails closed; an idle gap of
  any length refills as configured.
- **No capacity clamp.** `capacity()` equals `config().capacity()` for every
  `u32` (1.0 clamped at ~4.29 M and then denied in-capacity requests forever).
- **Slow rates refill on time.** One per day, week, 60 days or century — 1.0
  was 15.6% slow at one per week and never refilled below one per ~48.5 days.
- **Refill is never discarded.** A 1-token/hour bucket drained once a second now
  refills; 1.0 dropped the remainder on every grant.

The clock reading is converted to units by one 64×64-bit multiply with a rate
rounded up, so an exactly-due token (five tokens 500 ms into a 10/s bucket) is
granted on time and the retry hint says 500 ms. The only slack in the contract is
that a token may be granted a few nanoseconds before it is exactly due (or up to
2^-28 of a token early, for a bucket whose time to fill exceeds ~36 years).

## Proof, this time with a moving clock

- **`loom`** model-checks the real `Bucket` and `BucketCore` with the clock
  modelled as a loom atomic: an overtaken reader, two advances across three
  acquires, caller time from a shared atomic, and `reset` / `refund` /
  `reserve` races. The overtaken-reader model fails on 1.0.0.
- **A real-clock grant-ceiling test** runs 2–16 threads on `SystemClock` and
  bounds the total by capacity + rate × elapsed. 1.0.0 fails it by thousands of
  tokens.
- **Deterministic clock tests** stall a thread between its clock read and its
  CAS, and step a clock backwards.
- **`proptest`** drives `BucketCore` with arbitrary rates and arbitrary,
  including backward, time steps: every window of decisions is bounded by the
  exact refill, a frozen clock conserves every token, `available` is the exact
  grant boundary, the retry hint equals `time_until` and is honest, and
  reservations never commit more than they cover. A mutant whose clock runs one
  part per million fast fails the suite.
- **Miri**, the allocation audit, and the edge suite cover the rest.

## What's new

- **`BucketCore`** — the engine with the time supplied by the caller
  (`Duration` since any epoch). Needs only `core` and a 64-bit atomic; the
  optional `portable-atomic` feature covers Cortex-M and other targets without
  one — there as a global spinlock, so not lock-free and not interrupt-safe
  unless the binary enables portable-atomic's `unsafe-assume-single-core` or
  `critical-section` feature.
- **`*_at(now)` twins** of every clock-reading `Bucket` method, and `clock()`:
  read the clock once, decide for several buckets.
- **`with_config_and_clock`** / **`build_with_clock`** — one build, one clock
  read, for per-key buckets with an injected clock.
- **`time_until(n)`** — the `Retry-After` without spending a token; also on the
  `TokenBucket` trait, with `reset`. `None` always means "never"; the trait's
  provided body answers `Some(Duration::MAX)` when it cannot see a rate.
- **`reserve(n, max_wait)`** — take tokens ahead of their accrual and get the
  wait; later callers queue behind it, so a large request cannot be starved.
- **`refund(n)`** and **`acquire_up_to(n)`** — give back unused tokens; take
  what is there.
- **Features:** `serde` (validating `Deserialize` for `BucketConfig`),
  `metrics` (allowed / denied / granted-token counters, zero cost when off),
  `forge` (the `error-forge` impl, now optional for a core-only build and still
  implied by `clock`), `portable-atomic`.
- `const fn` `BucketConfig::new` and builder; `Hash` on `BucketConfig`,
  `Decision`, `BucketError`; `BucketError` works in `no_std`.
- `Bucket<SystemClock>` is one 64-byte cache line (it was two).

## Performance

The accounting costs about half a nanosecond more than 1.0 (~6.2 → ~6.7 ns
against a mock clock), the price of exact token units; with the real clock the
single-thread figure is within noise of 1.0 because the clock read dominates.
`BucketCore::acquire_at` with a supplied reading is ~4.5 ns. Denials no longer
write, so contended throughput improves where the bucket is actually
rate-limiting. On the same `Instant` clock `better-bucket` and `governor` are
within noise of each other on the test host; `governor`'s default `quanta` clock
remains faster out of the box. Full numbers in `docs/BENCHMARKS.md`.

## Breaking changes

**None.** `cargo semver-checks` passes against 1.0.0. Behaviour you may notice,
all of it bug or precision fixes: `capacity()` returns configured values above
~4.29 M; a few `retry_after` values are a millisecond shorter (more exact); a
bucket idle for more than 49.7 days refills fully; refill has nanosecond
resolution, so fast buckets accrue between whole milliseconds; and rates above
~4.3 × 10^9 tokens/second (sub-second periods only) charge grants in whole
multi-token units. See the CHANGELOG for the full list.
